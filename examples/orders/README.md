# Agentic OLAP · 订单、分笔支付与跨期退款

本应用从自含 DuckDB 原始数据出发，通过正式远程 MCP 完成源调查、定义建设、版本管理、发布、Query 校验和执行，再按精确引用消费结果与使用记录。Kotlin 准备者创建真实业务数据和作者明确给出的类型化定义模板，独立 Kotlin 客户端提交作者程序并消费正式回执。客户端不读取服务器文件或搬运私有发布产物。业务定义和独立预期由示例作者给出，不代表模型自主成绩。

## 输入与口径

订单、支付和退款有各自的真实记录身份。支付和退款都通过精确多对一关系引用原订单，不先拼成支付×退款明细。O1 的两笔支付60与40共同形成100支付额；退款的记录多重性不能因此翻倍。

| 原订单 | 客户 | 原单日期 | 支付 | 实际退款 |
| --- | --- | --- | ---: | --- |
| O1 | A | 2026-01-05 | 60＋40 | 1月退20；2月退10 |
| O2 | A | 2026-01-06 | 50 | 2月退5 |
| O3 | B | 2026-01-07 | 90 | 1月退10；2月退20 |
| P-A | A | 2025-12-01 | 100 | 12月退20 |
| P-B1 | B | 2025-12-02 | 100 | 12月退10 |
| P-B2 | B | 2025-12-03 | 70 | 12月退10 |

支付的发生日期与上表原单日期一致。另有一条客户及日期未知、尚无支付的登记订单，用来保留未知值的含义；它不能进入明确日期窗口，候选值排除NULL，也不自动补零。金额单位为 CNY。实际服务费另行登记：O1 收费5，O3 收费0；0是明确记录的免收费用。

共享净额计算体按客户分别完成支付和退款测量，再通过 `AlignMeasurements` 对齐并相减。同一 v1 定义的两个采用选择不同的精确时间映射：发生期采用按支付／退款自己的日期选期间，原单期采用按所引用原订单日期归属全部支付／退款。窗口使用左闭右开 `[start,end)`；退款观察截止于本例完整输入，原单期口径不是“只扣一月已发生退款”。

客户资格是实际 `Computed` 成员来源：本期订单数至少2且原单期净额至少100，结果只输出唯一客户身份，不公开中间净额或单数。客户净额先在计算体自己的ROOT完成，`Input` 完整读取原测量关系，保留其指标来源、客户唯一键和数量含义；资格名单作为独立RELATION，以显式 `JoinInput(SEMI)` 按客户键筛选这个完成关系，再按完整客户观察单位求和。筛选不放大左侧记录，不把名单反向写回支付、退款或资格来源。固定同群采用冻结一月名单，只让查询参数改变被测期间；另一采用将名单的期间也接到同一个查询参数，明确表示分别圈群。普通查询仍只选择采用与窗口，不需装配内部关系阶段。增长率定义在自己的ROOT中一次形成固定一月客户名单，以明确的 `LocalRef` 复用其完整客户身份；两个分支调用同一精确净额实例，分别提供一月和前期窗口，独立完成净额、筛选和统计后再求比率。局部复用不读取金额属性，也不把一份资格计算重复展开成两套；查询不能改写定义中固定的两个期间。

`ObservationStatistics` 区分订单、客户和真实订单数权重。均价始终使用 **gross支付总额240**，不把扣退款后的净额175当作gross。普通测量调用选择发布返回的精确 `instance`及剩余参数。`inline_two_periods`直接组织内联 `COMPUTE`，一次形成获准客户名单并独立测量两期；`inline_fixed_growth`在完整Query的具名输入中复用该计算，再按显式阶段比较。所需测量、成员输出、映射及阶段均经场景明确批准。客户端只组织DSL和核对独立预期。

## 可核算结果

一月窗口为 `[2026-01-01,2026-02-01)`，前期为 `[2025-12-01,2026-01-01)`。

| 查询 | 结果 | 含义 |
| --- | ---: | --- |
| occurrence_net | 210 CNY | 一月支付240减一月实际退款30 |
| original_net | 175 CNY | 一月原订单支付240减其全部退款65 |
| eligible_current | 115 CNY | A两单、净115合格；B一单、净60不合格 |
| fixed_prior | 80 CNY | 固定一月名单A的独立前期净额 |
| separately_prior | 150 CNY | 前期重新圈群得到B两单；A前期只有一单 |
| prior_total | 230 CNY | 独立前期总体A80＋B150，不被一月名单筛掉 |
| fixed_growth | 0.4375 | 同一客户A的 `(115−80)/80`，即43.75% |
| gross | 240 CNY | 三笔原订单对应的全部支付，O1两次支付保持 |
| order_mean | 80 CNY | gross240／真实订单3 |
| customer_mean | 120 CNY | 客户gross150与90的等权均值 |
| unweighted | 82.5 CNY | A每单75、B每单90，客户等权平均 |
| weighted | 80 CNY | 同一客户单价按真实订单数2／1加权 |
| updated_net | 170 CNY | 经营上下文明确采用共享v2，再扣实际服务费5 |
| retained_net | 175 CNY | 独立上下文继续精确采用已批准v1，形成新的发布 |
| inline_two_periods | 115／80 CNY | 调用者一次形成公开客户名单，独立完成本期与前期净额，再对齐 |
| inline_fixed_growth | 0.4375 | 完整Query的具名输入复用内联计算，再显式比较并投影 |

主发布 `orders-business@1` 保存v1及完整业务测量。随后共享定义修订到v2，经营主题域明确修订并重新组织自己的维度、采用和场景，形成 `@2`；独立主题域继续采用已变为 `DEPRECATED` 的精确v1，形成 `@3`。旧发布和旧查询保持原引用，不能因为共享定义当前版本改变而自动转用v2。公开目录中的定义／实例依赖说明所用结构、固定与可填参数、对象和数量合同，不授予私有依赖公共 ROOT 调用权。

金额求和与相减使用精确十进制合同；除法、均值和增长率声明有限评价域、原生浮点及显式容差。结果保留真实数量来源和观察单位，应用不把近似原生计算称为无限精度。业务预期来自上表输入，仅用于本应用核对；不能代替现实来源完整性证明。

## 运行与调用

在仓库根准备 JDK 21；产物目录必须不存在。

```sh
./project/gradlew -p project :development:orders
```

Gradle 装配同轮 JVM 发行与连接器，独立 Kotlin 研发客户端调用准备者产生真实来源，再持有临时签名者、HTTPS JWKS 和服务进程。客户端通过 MCP 完成建设与查询，观察外部认证、服务重启、无来源读取旧结果及外部业务新增数据。默认输出到 `.tmp/orders`，可用 `-Partifacts=/absolute/path` 指定。研发场景不属于产品业务工具。

客户端通过 MCP 提交 [main.olap.kts](main.olap.kts)，由程序调查原始表、采用实际列和关系，创建基础事实、共同维度、净额、资格和增长率等定义。资格规则是独立共享的 `MEMBER_DEFINITION`，激活后由主题域采用并绑定实际测量；计算定义可继续使用这些成员和测量。程序精确发布后执行上表查询，保存查询与结果，再明确复用。查询作者只持有正式类型与独立业务预期；结果读取保留原生数值、NULL 和数量含义。

场景重启服务后，将建设阶段正式返回的查询与结果引用作为参数，再次提交同一作者程序的 `reopen` 分支，读取保存查询、旧结果并重新执行。日常业务 Agent 连接实际服务的方式见[AI使用指引](../../docs/agent-usage.md)，来源、认证与预算配置见[服务使用说明](../../skills/agentic-olap/references/server.md)。

## 结果与持续变化的数据

`http/report.json` 保存建设、重启、无来源读取旧结果及来源变化等阶段的脚本回执，包含正式查询和结果引用。各阶段目录的 `mcp-calls.jsonl` 保存实际 MCP 请求与响应，其中 `execute-script` 请求保留本次完整作者程序。客户端文件不能授予服务器文件访问权或扩大后端权限。完整结果由服务器按调用者明确选择保存，通过正式结果读取、元数据、值分页和 profile 消费。

定义版本与数据快照是不同事实。Kotlin准备者的`advance-source`对原始支付表新增P5：O2在一月增加支付10；普通产品查询不提供写源工具。相同旧保存查询再次执行，原单期净额从175变为185，形成独立run；旧保存结果仍为175。精确发布固定语义与引用，不冻结持续变化的业务数据。

研发场景核实只读阶段源文件哈希不变。业务源、元数据与结果各自按实际生命周期持久化，不自动重试、补零、换版本或扩大预算。消息容量、部分成功恢复和安装后重启由独立的 npm 安装用法观察。
